주문 요청과 확정 결제의 역할을 나눕니다

Firestore는 주문 요청을 보관하고 MySQL은 확정 주문·결제의 원본을 관리하며, 고객과 판매자는 API로 같은 MySQL 결제 데이터를 조회하는 구조로 설계를 변경했습니다.

  1. 일반적인 서비스처럼 MySQL의 주문·주문 항목·결제를 관계형 테이블로 나누고, 함께 확정할 데이터는 하나의 트랜잭션으로 처리하도록 정했습니다.
  2. Firestore에는 고객이 제출한 주문 요청만 보관하고, 결제 데이터 복제와 Cloud Functions 기반 동기화는 새 설계에서 제외했습니다.
  3. 기존 코드·배포·시험 결과를 새 설계와 대조했습니다. 이번 수정은 보고서이며, API 전환·테이블 추가·새 구조의 전체 연결 시험은 아직 구현 전입니다.
새 설계와 현재 구현을 구분합니다. 이번 작업은 보고서 수정입니다. 현재 앱에는 이전 복제 코드가 남아 있으며 새 결제 API·주문 테이블은 아직 구현 전입니다.

일반적인 관계형 DB 관리 적용

  • 주문과 항목·결제를 외래키로 연결합니다.
  • 고객·요청 번호의 고유키로 중복 확정을 막습니다.
  • 구매 당시 상품명·가격은 주문 항목에 보관합니다.
  • 함께 확정할 MySQL 작업을 하나의 트랜잭션으로 처리합니다.
  • 결제·매출 원본과 브라우저 접근은 서버 API로 관리합니다.

orders·order_items 추가와 새로운 관계 제약은 설계이며 현재 DB에 적용된 상태가 아닙니다.

부분 실패를 숨기지 않는 처리 기준

상황처리
Firestore 접수 실패새 결제 확정 시작 안 함. 같은 요청 번호로 재시도.
Firestore 저장 후 MySQL 실패접수 기록은 남음. MySQL은 ROLLBACK하고 결제 성공으로 표시하지 않음.
MySQL 확정 후 응답 끊김같은 요청 번호로 기존 확정 결제를 찾아 반환.
같은 요청 번호·다른 상품이나 수량요청 내용 해시를 비교해 충돌 거부.
판매자 화면 갱신화면을 보는 동안 5초 조회 목표. 현재 구현은 15초로 아직 변경 전.

일반적인 MySQL 트랜잭션은 Firestore까지 한꺼번에 되돌리지 않습니다. 결제 복제 작업을 없애도 요청 재시도와 오류 안내는 필요합니다.
