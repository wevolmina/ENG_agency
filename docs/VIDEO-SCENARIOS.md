## 1. 촬영 전 준비

1. **판매자 계정과 권한부터 준비합니다.** 이메일 계정만 만들어서는 매출을 볼 수 없습니다. 관리 환경에서 해당 계정에 merchant_id=studio-mina 권한이 등록됐는지 확인하고 다시 로그인합니다. 관련 소스는 scripts/grant-merchant.mjs입니다. 권한 등록은 녹화 밖에서 진행합니다.
2. **두 화면을 미리 엽니다.** 왼쪽은 고객 상품 선택 화면, 오른쪽은 로그인과 매출 조회가 성공한 판매자 화면으로 둡니다. 비밀번호·인증코드 입력은 녹화에서 제외합니다.
3. **리허설과 본 촬영을 구분합니다.** 리허설 거래도 DB에 저장되고 매출에 포함됩니다. 기존 기록을 지우지 말고 본 촬영 직전의 매출과 거래 건수를 메모합니다.
4. **의뢰인 영상부터 촬영하는 순서를 권합니다.** 본 촬영에서 생성한 거래 번호를 기록하고, 개발자 영상에서는 같은 거래를 다시 설명합니다. 두 영상을 위해 불필요하게 새 결제를 만들 필요는 없습니다.
5. **고객의 익명 로그인 상태를 유지합니다.** 같은 브라우저를 사용하고 쿠키·사이트 데이터를 지우지 않습니다. 이전 영수증이 남아 있다면 ‘다른 상품 보기’로 돌아갑니다. 이전 미확정 요청 안내가 있다면 먼저 결과를 확인합니다.
6. **화면 배치를 점검합니다.** 가능하면 1920×1080 화면에 두 창을 좌우 배치합니다. 화면이 작아 모바일 배치가 되면 설명 중인 창을 잠깐 확대합니다. 알림과 자동 완성을 숨깁니다.

**촬영 시작 조건:** 판매자 권한과 실제 매출 조회가 준비되지 않았으면 ‘고객 결제 → 판매자 매출 반영’ 장면을 완성할 수 없습니다. 예시 숫자를 넣어 실제 운영 결과처럼 촬영하지 않습니다.

| 화면 위치 | 보여줄 화면 | 순서 |
| --- | --- | --- |
| 왼쪽 | 고객 스토어 | 상품 카드 → 주문 요약 → 영수증 |
| 오른쪽 | 판매자 센터 | 누적 매출 → 일별 차트 → 거래 목록 |

### 촬영용 거래 기준

| 항목 | 기준 |
| --- | --- |
| 상품 | 데일리 노트 / productId=starter |
| 단가·수량·총액 | 12,000원 × 2개 = 24,000원 |
| 판매자 | studio-mina 권한의 계정 |
| 결제 전 기준값 | 누적 매출 B원 / 거래 C건 |
| 결제 후 예상 변화 | 다른 거래가 없으면 누적 매출 B+24,000원 / 거래 C+1건 |
| 평균 결제 금액 | (B+24,000) ÷ (C+1), 화면에서는 원 단위 반올림 |
| 일별 차트 | 한국 시간 기준 촬영한 날짜의 매출 24,000원 증가 |
| 같은 거래 확인 | 고객 영수증과 판매자 거래 목록의 paymentId 일치 |
| 시간 주의 | 한국 시간 자정 전후를 피하고 같은 날짜 안에서 비교 |

## 2. MySQL과 Firebase DB는 어디서 보는가

### Firestore: Firebase 콘솔에서 주문 요청 보기

1. [paybridge-mock Firebase 콘솔](https://console.firebase.google.com/project/paybridge-mock/overview)을 엽니다.
2. 프로젝트를 관리하는 Google 계정으로 로그인합니다.
3. 왼쪽 Build(빌드) → Firestore Database → Data(데이터)를 엽니다.
4. 기본 데이터베이스에서 order_requests 컬렉션을 선택합니다.
5. 촬영한 주문의 문서를 열어 customerId, requestId, productId, quantity를 확인합니다.

컬렉션은 문서를 모은 묶음이고, 문서는 주문 요청 한 건입니다. order_requests에 기록이 있어도 결제 완료를 의미하지는 않습니다. 결제의 확정 기준은 MySQL입니다.

현재 결제 생성 소스에서 Firestore 문서 ID는 orderId입니다. 고객 영수증의 paymentId와 같은 이름의 문서를 찾는 방식은 아닙니다. MySQL payments 행의 order_id를 확인하면 Firestore 문서와 연결해 볼 수 있습니다.

### MySQL: Aiven 연결 정보를 이용해 조회 도구에서 보기

앞선 구성 기록의 MySQL 제공자는 Aiven입니다. 실제 서비스 이름과 DB 이름은 계정 화면에서 확인해야 합니다. Vercel은 서버와 판매자 화면을 실행하는 곳이며, MySQL DB 자체는 외부 서비스에 있습니다.

1. [Aiven 콘솔](https://console.aiven.io/)에 로그인합니다.
2. 조직 → 프로젝트 → 사용 중인 MySQL 서비스를 선택합니다.
3. Overview → Connection information에서 Host, Port, User, Database를 확인합니다. Password와 CA 인증서도 연결에 사용합니다.
4. MySQL Workbench 또는 DBeaver에서 해당 정보로 연결합니다. SSL/TLS와 CA 인증서 검증은 유지합니다.
5. 앱이 사용하는 DB를 선택한 뒤 orders, order_items, payments 테이블을 조회합니다. DB 이름을 임의로 payment_bridge 또는 defaultdb라고 단정하지 말고 실제 MYSQL_DATABASE 설정과 맞춥니다.

| 테이블 | 저장하는 내용 | 촬영에서 보여줄 부분 |
| --- | --- | --- |
| orders | 확정 주문 | order_id, request_id, amount, status |
| order_items | 구매한 상품과 수량 | order_id, product_name, unit_price, quantity |
| payments | 확정 모의 결제 | payment_id, order_id, amount, status |

조회 예시입니다. 연결한 DB를 먼저 선택하고 실행합니다. 데이터를 바꾸지 않는 SELECT만 사용합니다.

    SELECT payment_id, order_id, product_name, quantity, amount, status, created_at
    FROM payments
    WHERE merchant_id = 'studio-mina'
    ORDER BY created_at DESC
    LIMIT 10;

촬영에서는 Aiven 비밀번호·접속 URI·Authorization 헤더를 보여주지 않습니다. 주문을 확인할 때는 해당 거래만 조회하고 고객 식별값을 가립니다.

공식 안내:

- [Firebase 콘솔에서 Firestore 관리](https://firebase.google.com/docs/firestore/using-console?hl=ko)
- [Aiven MySQL과 MySQL Workbench 연결](https://aiven.io/docs/products/mysql/howto/connect-from-mysql-workbench)
- [Aiven MySQL과 DBeaver 연결](https://aiven.io/docs/products/mysql/howto/connect-with-dbeaver)

## 3. 개발자 영상에서 보여줄 구조 설명

### 호스팅·DB 역할

| 역할 | 실행·저장 위치 | 담당 내용 |
| --- | --- | --- |
| 고객 화면 | Firebase Hosting | 상품 선택·주문 요약·영수증 |
| 로그인 | Firebase Authentication | 고객 익명 인증 / 판매자 이메일 인증·판매자 권한 |
| 서버와 판매자 화면 | Vercel | 인증·가격 검증·주문 확정·영수증·매출 조회 |
| 주문 요청 | Cloud Firestore | order_requests에 고객·요청 번호·상품·수량 보관 |
| 확정 기록 | 외부 MySQL | orders / order_items / payments, 두 화면의 공통 결제 원본 |

신규 요청의 처리 순서: 고객 화면 → Vercel API → Firestore 주문 요청 접수 → MySQL 확정 → 고객 영수증·판매자 조회.

이미 확정된 같은 요청은 MySQL에서 먼저 찾아 반환합니다.

### 초기 검토안과 현재 배포 구조

| 항목 | 초기 검토안 | 현재 배포 구조 |
| --- | --- | --- |
| 결제 최종 기준 | Firestore 결제 원본 | MySQL 확정 결제 |
| Firestore 역할 | 결제 데이터·동기화 상태 | 주문 요청 접수 |
| 서버 처리 위치 | Firebase Cloud Functions | Vercel API |
| MySQL 역할 | 복제된 결제를 판매자 조회에 사용 | 확정 주문·항목·결제 원본 |
| DB 간 연결 | 같은 결제의 복제·동기화 | API가 요청 접수 후 MySQL 확정 |
| 트랜잭션 범위 | 현재 구현과 구분해서 설명 | MySQL 내부 주문·항목·결제 |
| 배포 경로 | Functions 배포 조건 때문에 중단됐던 경로 | Firebase Hosting + Vercel, Functions 제외 |

초기 구성은 검토·구현 과정의 이전 설계입니다. 실제 운영 DB를 이관하거나 삭제한 것처럼 설명하지 않습니다. functions 폴더에 과거 소스가 남아 있어도 현재 운영 경로에서 Cloud Functions를 실행한다는 뜻은 아닙니다. 현재 결제 API는 /api/checkout이며 이전 복제 수신 API는 사용 종료 응답을 반환합니다.

### 실패·재시도 기준

| 상황 | 구현 처리 | 핵심 설명 |
| --- | --- | --- |
| Firestore 접수 실패 | 신규 MySQL 확정 시작 안 함 | 접수와 결제 완료 구분 |
| 접수 성공, MySQL 실패 | Firestore 요청은 남고 MySQL은 롤백 | 같은 요청 번호로 재시도 |
| MySQL 성공, 응답 유실 | 같은 요청 번호로 기존 확정 기록 조회 | 응답 실패를 곧바로 결제 실패로 단정하지 않음 |
| 같은 요청 번호·같은 내용 | 기존 결과 반환, 고유 제약·행 잠금으로 동시 확정 제어 | 중복 결제 방지 |
| 같은 요청 번호·다른 내용 | 409 REQUEST_CONFLICT | 다른 내용으로 재사용 거절 |
| 판매자 조회 실패 | 오류 표시, 확정 결제는 유지 | 매출 조회 오류와 결제 취소는 다름 |

## 4. 영상 1: 처음 보는 개발자를 위한 설명 / 약 7분

코드 전체를 빠르게 스크롤하지 말고, 멘트 사이에 파일 위치와 핵심 코드 3~5줄을 짚는 시간을 둡니다.

### 01. 무엇을 구현했는가 / 00:00–00:30

**화면과 조작:** 고객·판매자 운영 화면을 나란히 보여줍니다. 주소창의 서로 다른 도메인을 3초씩 확대합니다.

**그대로 읽는 설명 멘트**

> 이 서비스는 하나의 모의 결제를 고객에게는 영수증으로, 판매자에게는 매출 현황으로 보여줍니다. 고객 화면은 Firebase Hosting, 판매자 화면과 서버 API는 Vercel에 배포했습니다. 지금부터 두 화면 사이에서 데이터가 어떻게 처리되는지 설명하겠습니다.

**자막:** 고객 화면 / 판매자 화면 · 실제 카드 청구 없음

**확인:** 두 화면이 모두 열려 있어야 합니다. 판매자 로그인은 녹화 전에 완료합니다.

### 02. 초기 설계에서 무엇이 바뀌었는가 / 00:30–01:20

**화면과 조작:** 설계 변경 비교표를 보여줍니다. 초기 설계는 ‘검토안’, 현재 구조는 ‘배포된 구조’로 표시합니다.

**그대로 읽는 설명 멘트**

> 초기에는 Firestore에 결제를 저장하고 Cloud Functions를 통해 MySQL로 같은 결제를 복제하는 구조를 검토했습니다. 이후 역할을 바꿨습니다. 현재 Firestore는 고객의 주문 요청을 보관하고, MySQL은 확정 주문과 결제의 최종 기록을 관리합니다. 결제 처리와 조회는 Vercel 서버가 맡습니다. 현재 배포 경로에서는 Cloud Functions와 DB 간 결제 복제를 사용하지 않습니다.

**자막:** 초기 검토안 → 주문 요청과 확정 결제의 역할 분리

**확인:** 이전 구성이 운영되다가 이관된 것처럼 설명하지 않습니다. DB 삭제·운영 데이터 이전을 시연하지 않습니다.

### 03. 호스팅과 DB의 위치 / 01:20–02:00

**화면과 조작:** 역할 표를 보여준 뒤 apps/customer, apps/merchant, database 폴더를 차례로 엽니다.

**그대로 읽는 설명 멘트**

> 호스팅은 프로그램을 실행하고 웹 화면을 제공하는 곳입니다. 데이터베이스는 기록을 보관하는 곳입니다. Vercel에서 MySQL 자체를 실행하는 것이 아니라, Vercel의 서버가 외부 MySQL에 연결합니다. Firebase Hosting은 고객 화면을 제공하고, Firestore는 별도로 주문 요청을 저장합니다. 두 화면이 서로 다른 곳에 배포되어도 같은 결제 기록을 조회할 수 있습니다.

**자막:** Hosting = 화면 제공 / API = 요청 처리 / DB = 기록 보관

**확인:** 비밀 환경 변수와 DB 접속 정보를 열지 않습니다. DB 조회 위치는 이 문서 2장을 참고합니다.

### 04. 고객 요청이 서버까지 가는 과정 / 02:00–03:00

**화면과 조작:** 고객 main.tsx의 pay → checkout/route.ts의 POST → checkout.ts의 recordRequest 순서로 보여줍니다. 이미 촬영한 거래의 Network 요청에서 필드 이름만 보여줍니다.

**그대로 읽는 설명 멘트**

> 고객은 상품과 수량을 선택합니다. 브라우저는 상품 번호, 수량, 요청 번호를 서버에 보냅니다. 금액은 고객이 보낸 값을 믿지 않고 서버의 상품 가격으로 계산합니다. 서버는 로그인과 입력을 검사하고, 이미 확정된 요청인지 먼저 확인합니다. 신규 요청이면 Firestore의 order_requests에 기록한 다음 MySQL 확정을 시작합니다. Firestore에 요청이 있다는 것만으로 결제 완료는 아닙니다.

**자막:** productId + quantity + requestId / 가격은 서버 계산

**확인:** Authorization 헤더는 펼치지 않습니다. Firestore는 해당 문서만 열고 고객 식별값을 가립니다. 개발자 영상을 위해 새 결제를 추가하지 않습니다.

### 05. MySQL 트랜잭션과 중복 방지 / 03:00–04:10

**화면과 조작:** checkout.ts의 confirmOrder와 database/002-orders.sql을 엽니다. beginTransaction → 주문 → 항목 → 결제 → commit을 강조합니다.

**그대로 읽는 설명 멘트**

> 트랜잭션은 함께 처리해야 하는 저장 작업을 한 묶음으로 확정하거나 취소하는 기능입니다. 여기서는 주문, 주문 항목, 결제를 같은 MySQL 연결에서 처리합니다. 중간 저장이 실패하면 모두 롤백합니다. 고객과 요청 번호의 고유 제약 및 요청 내용 검사를 사용해 같은 요청이 중복 결제로 확정되는 것을 막습니다. 단, 이 트랜잭션은 MySQL 내부에만 적용됩니다. Firestore 기록까지 함께 되돌리는 분산 트랜잭션은 아닙니다.

**자막:** BEGIN → orders → order_items → payments → COMMIT / 실패 시 ROLLBACK

**확인:** 운영 DB에 오류를 일부러 넣지 않습니다. 오류·동시 요청은 기존 테스트 소스를 설명하는 장면으로 대체합니다.

### 06. 같은 결제가 두 화면에 다르게 보이는 이유 / 04:10–05:00

**화면과 조작:** 고객 영수증과 판매자 거래 목록의 같은 상품·금액·결제 번호를 번갈아 확대합니다. 결제 번호의 같은 끝 6자리를 표시합니다.

**그대로 읽는 설명 멘트**

> 고객 영수증은 본인 결제 한 건을 자세히 보여줍니다. 판매자 화면은 같은 MySQL 결제를 매출 합계와 일별 차트, 거래 목록으로 보여줍니다. 데이터가 두 DB에 복제되어서 화면이 바뀌는 것이 아닙니다. 같은 결제 원본을 목적에 맞게 조회해서 다르게 표현하는 것입니다. 판매자 화면은 탭이 보이는 동안 5초 간격으로 다시 조회합니다.

**자막:** 동일 paymentId / 영수증 ↔ 매출·차트·거래 목록

**확인:** 누적 매출은 전체 기간, 차트는 최근 30일, 거래 목록은 최근 100건입니다. 세 영역의 조회 범위가 같다고 설명하지 않습니다.

### 07. 실패와 재시도는 어떻게 처리하는가 / 05:00–06:00

**화면과 조작:** 실패 처리 표, existingOrder 코드, 관련 테스트 이름을 보여줍니다. 실제 운영 장애는 만들지 않습니다.

**그대로 읽는 설명 멘트**

> Firestore 접수가 실패하면 신규 MySQL 확정을 시작하지 않습니다. 접수 뒤 MySQL 저장이 실패하면 Firestore 요청은 남고 MySQL 작업은 롤백됩니다. MySQL 저장 후 응답만 끊겼다면 같은 요청 번호로 재시도할 때 기존 결제를 반환합니다. 같은 번호에 다른 상품이나 수량을 넣으면 충돌로 거절합니다. 자동 복구 큐는 없으므로, 이 구현에서는 같은 요청으로 재시도하는 방식으로 결과를 확인합니다.

**자막:** 요청 접수 ≠ 결제 완료 / 같은 요청 번호로 결과 확인

**확인:** 새로고침으로 영수증을 복원하는 기능과 동일 요청 재시도는 다른 기능입니다. 새로고침만 보여주고 중복 요청 테스트를 했다고 말하지 않습니다.

### 08. 검증 범위와 인수인계 / 06:00–07:00

**화면과 조작:** 검증 상태 표와 소스 링크를 보여주고 마지막에 두 운영 주소를 표시합니다.

**그대로 읽는 설명 멘트**

> 이번 화면 변경에서는 고객과 판매자 빌드 및 기존 단위 테스트 17건을 확인했습니다. 배포된 고객 화면에서 상품·수량에 따른 금액과 동의 여부에 따른 버튼 동작도 확인했습니다. 과거 운영 API 검증 12항목은 이전 기록으로 따로 남아 있습니다. 판매자 로그인 후 같은 거래가 반영되는 장면은 촬영 전에 다시 확인해야 합니다. 실제 카드 승인과 정산을 연결한 서비스는 아니며, 현재 결과는 모의 결제입니다. 소스와 운영 주소를 전달드리겠습니다.

**자막:** 확인한 결과 / 촬영 전 확인할 결과 구분

**확인:** 판매자 연동 리허설을 실제로 마쳤다면 확인한 결제 번호와 결과만 추가합니다. 문서 작성 자체를 시험 완료로 표현하지 않습니다.

## 5. 영상 2: 의뢰인을 위한 고객·판매자 시연 / 약 4분

### 01. 두 화면 소개 / 00:00–00:20

**확인:** 상품명과 주문 요약이 일치해야 합니다. 수량은 다음 장면에서 바꿉니다.

**자막:** 안내 확인 → 결제 버튼 활성화

**그대로 읽는 설명 멘트**

**자막:** 매출 B + 24,000원 / 거래 C + 1건

**확인:** 자동 조회는 실시간 푸시가 아닙니다. 기준값 비교 중에는 다른 모의 결제가 들어오지 않도록 합니다.

**자막:** 기존 영수증 다시 보기 / 새 결제 아님

## 10. 판매자 테스트 계정은 무엇인가

현재 이 작업에서 생성·전달한 판매자 테스트 이메일과 비밀번호는 없습니다. 기존 보고서에서도 판매자 계정·권한 준비가 남은 항목으로 기록되어 있습니다. Firebase Authentication의 실제 계정 목록은 이 문서 작성 중 별도로 열람하지 않았으므로, 이미 다른 작업에서 만든 계정이 있는지는 콘솔에서 확인해야 합니다.

| 항목 | 현재 안내 |
| --- | --- |
| 로그인 이메일 | 확인·전달된 테스트 이메일 없음 |
| 비밀번호 | 공개 README에 기록하지 않음. 생성 시 정한 값을 별도로 관리 |
| 판매자 권한 | merchant_id=studio-mina |
| studio-mina의 의미 | 로그인 아이디가 아니라 이 스토어의 매출을 조회할 권한 값 |
| 일반 이메일 계정만 있는 경우 | 로그인은 가능해도 판매자 권한이 없으면 매출 조회가 거절됨 |

### 준비 순서

1. Firebase 콘솔에서 paybridge-mock 프로젝트 → Authentication → Users(사용자)를 엽니다.
2. 테스트용 이메일 계정이 이미 있는지 확인합니다. 없다면 Add user(사용자 추가)로 본인이 관리하는 테스트 이메일과 비밀번호를 등록합니다. 비밀번호 입력은 녹화 밖에서 진행합니다.
3. 해당 계정의 UID(사용자 고유 식별값)를 확인합니다.
4. 이 프로젝트의 Firebase Authentication 관리 권한이 있는 인증 환경에서 저장소 루트의 아래 명령을 실행합니다. 실제_UID 부분을 방금 확인한 UID로 바꿉니다. 별도 웹 로그인으로 판매자 권한이 자동 부여되지는 않습니다.

    FIREBASE_PROJECT_ID=paybridge-mock npm run merchant:grant -- "실제_UID" studio-mina

이 명령은 Git Bash용입니다. 먼저 npm install이 되어 있어야 하며, 스크립트는 Application Default Credentials(기본 애플리케이션 인증 정보)를 사용합니다. firebase login 성공만으로 이 관리자 인증이 준비됐다고 단정할 수 없습니다. 승인된 관리자 인증이 없으면 관리자 환경을 먼저 준비해야 합니다. 서비스 계정 비밀 키를 README나 저장소에 올리지 않습니다.

5. 권한 등록이 끝나면 판매자 화면에서 로그아웃 후 다시 로그인합니다.
6. 매출 카드·차트·거래 목록이 정상 조회되는지 확인한 뒤 촬영을 시작합니다.

비밀번호나 ID 토큰을 채팅 또는 공개 문서에 붙여넣지 않습니다. 이 문서를 올리는 작업에서는 계정 생성이나 관리자 권한 부여를 수행하지 않습니다.
