# 관리자·판매자 권한 신청

로그인한 계정으로 신청하면 MySQL에 저장하고 마스터가 화면에서 수락·거절합니다. UID(User Identifier, 사용자 고유 식별값)는 서버가 인증 정보에서 확인하므로 따로 전달하지 않습니다.

## 화면 사용법

1. 로그인 → 내 계정 → 이용 권한 신청에서 판매자 또는 관리자를 선택합니다.
2. 마스터는 관리자 사이트의 계정·권한 → 등록 상태 확인에서 신청을 봅니다.
3. 수락 또는 거절을 누릅니다. 거절 사유는 선택 사항입니다.
4. 신청자는 신청 상태 확인으로 결과를 확인합니다. 대기 중에는 화면이 보이는 동안 15초마다 자동 확인합니다.
5. 거절 후 다시 신청할 수 있습니다. 기존 계정 권한도 마스터가 역할별로 해제할 수 있습니다.

수락 전에는 해당 기능을 사용할 수 없습니다. 일반 관리자는 다른 계정의 신청을 처리할 수 없습니다. 마스터의 수락·거절·해제는 기존 정책대로 구글 로그인 후 5분 이내에 가능합니다. 시간이 지나면 로그아웃 후 구글로 다시 로그인합니다.

## DB와 API

| 테이블 | 저장 내용 |
| --- | --- |
| staff_access_requests | 계정·상점·역할별 최신 신청과 현재 상태 |
| staff_access_request_reviews | 수락·거절의 누적 기록, 처리자·사유 |
| staff_memberships | 실제 접근 권한 |
| staff_access_audit | 기존 승인·해제 기록 |

신청은 권한을 부여하지 않습니다. 수락할 때 신청한 역할만 부여하고 권한·결과·처리 기록을 하나의 트랜잭션으로 저장합니다. 일부라도 실패하면 전체를 취소합니다. 거절은 기존 권한을 해제하지 않으며 해제는 별도 버튼에서 처리합니다.

같은 역할의 대기 신청은 중복 저장하지 않습니다. 재신청에 새 신청 번호를 부여해 과거 화면의 버튼으로 새 신청을 처리하지 못하게 합니다. 이전 수락·거절 기록은 유지합니다. 대기 목록은 오래된 순으로 최대 100건이며 다음 신청이 있으면 안내합니다.

- GET /api/staff/requests: 본인의 신청·권한만 조회
- POST /api/staff/requests: role만 받아 신청. UID·이메일·상점 주입 거절
- GET /api/admin/access: 마스터에게 대기 목록·처리 이력 제공
- POST /api/admin/access: action=review, requestId, decision, reason으로 처리. 마스터 신원과 최근 로그인 재검사

Firebase는 로그인 신원을 확인하고 MySQL이 접근 권한을 판단합니다. Firebase 사용자 클레임에 역할을 새로 저장하는 방식이 아닙니다. 이메일·UID는 눈 버튼으로 개별 표시합니다. 비밀번호·서비스 계정 비밀값은 신청 DB에 저장하지 않습니다.

## 코드와 배포

- apps/merchant/lib/staff-access.ts: 신청과 승인 트랜잭션
- apps/merchant/lib/staff-requests-http.ts: 신청 API의 인증·입력 검사
- packages/staff-ui/StaffRequests.tsx: 신청자 화면
- packages/staff-ui/StaffAccess.tsx: 마스터 신청 처리

기존 서버의 MySQL 환경에서 npm run db:migrate로 database/005-staff-access-requests.sql을 적용할 수 있습니다. 첫 인증된 신청에서도 CREATE TABLE IF NOT EXISTS로 신규 두 테이블을 준비합니다. 서버 계정에 CREATE 권한이 없다면 먼저 마이그레이션 계정으로 SQL을 적용합니다. 조회 요청은 테이블을 만들지 않습니다.

기존 마스터·권한은 유지합니다. 신규 환경에서는 최초 마스터 등록이 먼저 필요합니다. 판매자/API와 관리자 앱을 모두 배포해야 새 흐름을 사용할 수 있습니다.

## 검증 · 2026-10-26

- 전체 단위 테스트 83개 통과. 신규 10개 시나리오: 중복 신청, 본인 한정 조회, 역할별 수락, 거절·재신청, 일반 관리자 차단, 다른 상점 충돌, 입력·출처 제한, 비회원·중지 계정 차단, 이력 저장 실패 전체 롤백 등.
- 관리자·판매자 TypeScript 검사, 관리자 Vite 빌드 통과.
- 판매자 Next.js 빌드 통과. 초기 기본 출력 폴더에서 patchFetch 오류가 발생했으나 별도 출력 폴더·단일 작업자 재검사는 정상 완료했습니다. 임시 빌드 설정은 커밋하지 않습니다.
- 가짜 인증·API 응답으로 브라우저에서 신청 → 수락 → 결과 확인 → 다른 역할 신청 → 사유와 함께 거절 → 재신청 → 권한 해제를 검증했습니다. 너비 320·390·768·1440에서 가로 넘침과 페이지 오류가 없었습니다.
- 운영 계정의 실제 신청·권한 변경, 운영 MySQL 마이그레이션, 운영 배포는 수행하지 않았습니다. 실제 MySQL 동시 실행은 별도 통합 시험이 필요합니다.
